# GRAFIX 4.1 — SOLVER IMPLEMENTATION PLAN

## Sprint P0.1

Goal: add a real CP-SAT backend behind the existing `SolverAdapter` boundary while preserving the 4.0 heuristic backend.

## Backend choice

Primary backend: Google OR-Tools CP-SAT compiled to WebAssembly through `or-tools-wasm` 0.9.1.

Rationale:
- real CP-SAT engine, not a heuristic imitation;
- Node-compatible;
- WASM avoids shipping a separate Python runtime;
- Windows x64 is not tied to a platform-specific native solver binary;
- Apache-2.0 license;
- can run in an isolated Node worker so renderer/main UI remains decoupled from search.

The package is a third-party WebAssembly distribution of upstream Google OR-Tools, not an official Google Node binding. This is a dependency-governance item for later production certification.

## Process boundary

`SolverAdapter` remains the stable application boundary.

`CpSatSolverAdapter` starts a dedicated `worker_threads` worker:

```text
UI / main
  |
  +-- SolverAdapter
        |
        +-- CpSatSolverAdapter
              |
              +-- solver-cp-sat-worker.js
                    |
                    +-- or-tools-wasm/cp-sat
```

No solver execution is placed in the renderer process.

## Compatibility

The existing synchronous `SolverAdapter.solve()` remains heuristic-backed for 4.0 compatibility.

4.1 adds asynchronous solver methods which default to CP-SAT:
- `solveAsync(db, options)`;
- `validate(db, options)`;
- `generateAlternatives(db, options)`.

`backend: 'heuristic'` remains available for fallback/benchmark comparison.

## Model scope in P0.1

Current 4.0 `lessons` remain the input object. The richer `Activity` model is deferred to P0.4.

Implemented CP-SAT hard feasibility model:
- exactly one candidate placement per movable lesson;
- exact placement preservation for locked lessons;
- teacher collision exclusion;
- group collision exclusion;
- room collision exclusion;
- working hours;
- allowed days;
- teacher/group/room unavailable intervals;
- room capacity;
- room type;
- branch-scoped rooms;
- blocked slots;
- existing locked-resource occupancy.

First-stage objective terms:
- late lessons;
- teacher preferred-day violations.

The remaining 4.0 soft scoring terms remain in the heuristic benchmark and are not silently re-labeled as CP-SAT objectives until represented explicitly in the CP model.

## Status model

Application-facing statuses:
- `OPTIMAL`
- `FEASIBLE`
- `INFEASIBLE`
- `UNKNOWN`
- `MODEL_INVALID`
- `TIME_LIMIT`

The adapter never converts `FEASIBLE` to `OPTIMAL` and never converts `INFEASIBLE` into generic generation failure.

## Result contract

At minimum:
- `status`
- `elapsedMs`
- `hardViolations`
- `softPenalty`
- `objective`
- `bestKnown`
- `solverBackend`
- `seed`
- `timedOut`
- `lockedActivities`
- `lessons`
- `modelStats`

## Time limits

Supported options:
- 1 sec
- 5 sec
- 10 sec
- 30 sec
- 60 sec

Arbitrary positive values are accepted by the backend, but the listed values are the certification set.

## Determinism

Acceptance configuration uses one CP-SAT search worker by default and a fixed seed. Multi-worker configurations remain available for later performance tuning but are not used for deterministic certification.

## Multiple solutions

`generateAlternatives()` solves the same objective model repeatedly with a no-good constraint blocking the exact prior assignment. This guarantees actual solution differentiation when at least two feasible assignments exist; random seeds are also varied between solutions.

## Fallback

The heuristic backend is retained for:
- fast preview;
- warm-start/reference comparisons;
- repair fallback;
- benchmark baseline.

CP-SAT fallback is not automatic when a model is infeasible: `INFEASIBLE` must remain visible to the caller.

## Packaging implications

`or-tools-wasm` is a runtime dependency of the 4.1 development branch. The existing Electron packaging configuration must include the solver worker/model files. No remote service or API key is required.

The package-lock file is absent from the supplied 4.0 source artifact, so no historical lockfile is fabricated in this sprint. A lockfile should be generated by the first Windows-connected dependency installation before a distributable 4.1 package is certified.


## Electron worker integration gate (P0.1)

The solver boundary is exposed through the existing secure Electron preload/main path without adding UI. The 4.1 gate uses `solverValidate`, `solverSolve`, `solverAlternatives`, `solverDiagnose`, and `solverCancel`. The dedicated runtime test is `npm run test:electron-solver`. This is an implementation prerequisite for the required real Electron acceptance; no PASS is claimed until it executes with `or-tools-wasm@0.9.1` on Windows.
