# РИТМ 2.1.0 — forensic persistence release report

## Корневая причина

Подтверждён конкретный дефект IPC-контракта сохранения.

`preload.js` передавал обычное сохранение через:

```text
invoke('save-local-data', { data: payload })
```

а синхронное сохранение при закрытии — непосредственно:

```text
sendSync('save-local-data-sync', payload)
```

`main.js` обрабатывал оба канала как будто они получают одинаковый payload. Поэтому для async-сохранения `revision` находился не на ожидаемом уровне объекта и фактически становился `0`. Механизм защиты от устаревших сохранений не работал.

При закрытии синхронное сохранение одновременно использовало другой формат сериализации. В результате после обычной работы на диске могли существовать разные форматы состояния, а ожидаемые метаданные `revision/savedAt/activeBranchId` могли исчезать.

Это создавало реальную гонку:

```text
async save revision 5 ───────────────┐
                                     ├─ старый снимок
shutdown sync revision 6 ── запись ──┘
                                     ↓
старый async save мог записать revision 5 поверх final state
```

## Исправление

Введён единый `storage-manager.js`.

Единый формат файла:

```json
{
  "version": "2.1.0",
  "revision": 123,
  "savedAt": "2026-09-21T00:00:00.000Z",
  "activeBranchId": 2,
  "data": {
    "organization": {},
    "branches": [],
    "teachers": [],
    "rooms": [],
    "people": [],
    "lessons": [],
    "printSettings": {}
  }
}
```

Оба IPC-канала теперь принимают **один и тот же объект без дополнительной обёртки**.

Storage manager:

- читает текущую revision с диска;
- отклоняет устаревшую revision;
- делает backup предыдущего файла;
- пишет во временный файл;
- вызывает fsync;
- заменяет основной файл атомарно;
- восстанавливает повреждённый primary из backup;
- предоставляет диагностические данные.

## Renderer persistence

`localStorage` теперь используется как recovery mirror, а не как второй независимый источник истины.

При запуске сравниваются revision диска и revision mirror. При более свежем mirror выполняется контролируемое восстановление на диск.

При закрытии установлен отдельный guarded synchronous save. Повторный `beforeunload/pagehide` не создаёт второй конкурирующий shutdown-save.

## Что не проверено здесь

В текущей среде отсутствует установленный Electron runtime (`node_modules/.bin/electron` отсутствует) и ранее не удалось скачать зависимости из npm registry. Поэтому:

- реальный запуск Electron — **НЕ ПРОВЕРЕНО**;
- реальный Windows UI restart — **НЕ ПРОВЕРЕНО**;
- NSIS installer — **НЕ ПРОВЕРЕНО**;
- Portable EXE — **НЕ ПРОВЕРЕНО**;
- установка/удаление EXE — **НЕ ПРОВЕРЕНО**.

Для Windows добавлен `electron_persistence_test.bat`, который после `npm install` запускает именно `main.js` приложения в двух отдельных Electron-процессах: первый записывает данные, второй загружает их из того же `userData` каталога и проверяет результат.
